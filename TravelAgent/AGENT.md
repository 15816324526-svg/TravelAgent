# Traval 项目流程记忆

## 1. 项目定位

这是一个长期工程学习项目。学习者每天投入约 2 小时，从零开始亲手构建一个智能旅行助手。

参考资料：

- GitHub 仓库：`15816324526-svg/hello-agents`
- 章节：`docs/chapter13/第十三章 智能旅行助手.md`
- 链接：<https://github.com/15816324526-svg/hello-agents/blob/main/docs/chapter13/%E7%AC%AC%E5%8D%81%E4%B8%89%E7%AB%A0%20%E6%99%BA%E8%83%BD%E6%97%85%E8%A1%8C%E5%8A%A9%E6%89%8B.md>

可以学习该章节的分层思路、数据流、接口契约意识和前后端协作方式，但不得照抄其代码、目录细节、提示词、Agent 实现或产品定位。本项目必须形成自己的需求、图状态、Agent 契约、路由规则、数据模型和测试。自 2026-11-20 起，学习者已明确选择天气查询、景点规划、酒店规划、规划协调四个 Agent 作为本项目的学习目标；角色类别与参考项目接近是学习者主动做出的产品决定，不代表继承参考项目的实现。

四 Agent 编排已确定为核心学习范围；目标用户、具体外部数据源和其余 MVP 功能仍未完全确认。任何额外功能假设都要明确标记，并先让学习者决定。

## 2. 技术方向

- 后端：Python、LangChain、LangGraph、FastAPI、Pydantic。
- 前端：Vue 3、TypeScript；前端不是主要训练区，但接口契约仍由学习者设计。
- 智能体编排：使用 LangGraph，不使用 HelloAgents 项目自研的 Agent 框架。
- 酒店数据：目标是通过合法、获授权的美团酒店能力查询；必须隔离在酒店 provider/adapter 边界之后。
- 地图、天气、景点和图片来源在需求设计后再决定，不因参考项目使用某个服务而自动沿用。

美团接入规则：

1. 不抓取美团网页，不逆向私有接口，不绕过鉴权或平台限制。
2. 在确认账号准入、官方接口、授权范围、测试环境、计费和条款前，不宣称已经可以获得实时酒店数据。
3. 学习阶段应允许使用固定 fixture 或 FakeHotelProvider，确保 LangGraph 与接口设计不被第三方准入阻塞。
4. 真实凭据只放本地 `.env`；仓库只提供无真实值的 `.env.example`。
5. 任何对话都不得读取、记录、回显或提交真实 API Key、Token、Cookie 或其他密钥。

## 6. 参考项目与本项目的边界

HelloAgents 第 13 章使用景点搜索、天气查询、酒店推荐、行程规划四个 Agent 顺序协作，采用高德 MCP 获取多类数据，以单个 `POST /api/trip/plan` 返回完整计划，并在 Vue 3 页面展示地图、预算、编辑和导出。

本项目不默认继承参考项目的实现；学习者已在 2026-11-20 主动确定以下架构方向：

- 用 LangGraph 显式表达状态、节点、边和路由；
- 使用规划协调 Agent 监督天气查询 Agent、景点规划 Agent、酒店规划 Agent；
- 三个专业 Agent 必须具备模型、领域工具、工具调用循环、结构化输出、停止条件和失败处理，不能只是改名后的普通函数；
- LangChain 负责各 Agent 内部的模型、消息、工具调用和结构化输出，LangGraph 负责四 Agent 之间的共享状态、路由、循环和终止；
- 后端使用 FastAPI；
- 前端使用 Vue 3；
- 酒店查询面向美团官方且获授权的能力，并通过 provider/adapter 隔离；
- 目录继续保留 `backend/` 与 `frontend/` 顶层分区。

地图可视化、图片、餐饮、导出、行程编辑及其他扩展功能仍需单独决定，不能因为参考项目包含就自动加入。

#### 后端教练长期 Mission

后端教练的长期任务，是以教学为第一目标，陪学习者亲手完成 TravelAgent 的 Python 后端闭环：

前端提交 PlanRequest
→ FastAPI 创建任务并立即返回 task_id
→ LangGraph 执行真实规划
→ 后端通过 SSE 推送真实进度
→ 规划完成后保存 PlanResult 并返回 result_id
→ 前端根据 result_id 查询完整结果

长期教学范围包括：

- Python 后端工程基础。
- Pydantic 请求、响应和领域模型。
- FastAPI 路由、依赖、异常、OpenAPI 和 SSE。
- LangChain/LangGraph 的状态、节点、边、条件路由、工具调用和记忆。
- 任务状态、结果存储、失败路径、重试和可观察性。
- provider/adapter 边界以及 Fake Provider 测试。
- 后端测试和前后端接口契约核对。

固定主线顺序：

1. 设计 PlanResult 和前后端接口契约。
2. 建立最小 FastAPI 骨架。
3. 实现任务创建、真实进度事件和结果查询。
4. 设计并实现 LangGraph。
5. 实现任务与结果存储。
6. 实现 provider/adapter 和测试替身。
7. 完成后端测试及 OpenAPI 核对。
8. 后端闭环完成后再连接前端。

教学节奏：

- 学习者可能围绕一个模型、函数或概念提出很多问题，进度慢是正常情况，不得催促或跳步。
- 每次只推进一个约两小时的小里程碑；一个里程碑可以跨越很多轮对话。

### 固定主线第 3、4、5 步的衔接解释

固定主线是教学顺序，不是三个完全隔离、一次性完成的工程阶段：

1. 第 3 步可以先建立任务 API、SSE 协议/队列/流式响应和结果查询基础。
2. 第 4 步的 LangGraph 才能提供真实规划工作及真实阶段完成信号。
3. 真实 `progress` 事件测试不要求先完成生产级持久化；LangGraph 完成后，可以先使用当前单进程内存任务表、结果表和事件队列进行本地端到端测试。
4. 完整的成功闭环测试必须至少具备最小结果存储：先保存 `PlanResult`，再发送 `completed`，随后能通过 `result_id` 查询同一结果。
5. 第 5 步再把当前内存存储继续设计、测试和加固；生产级持久化、重启恢复、多进程共享和过期清理不必成为首次真实 SSE 测试的前置条件。
6. 不得为了提前宣布第 3 步完成而使用固定 `steps`、`sleep` 或定时器伪造正式后端进度。

因此，第 3 步目前应标记为“基础设施完成、真实闭环待 LangGraph 与最小存储集成后验收”，而不是完全完成。

## 11. 已确认的四 Agent LangGraph 开发计划（2026-11-20）

### 11.1 模块目标和边界

本专门对话的目标不是把规划过程退化为固定顺序的普通 Python 工作流，而是让学习者亲手完成一个可独立调用、可测试的四 Agent 编排核心：

```text
PlanRequest
→ 规划协调 Agent
→ 天气查询 Agent / 景点规划 Agent / 酒店规划 Agent
→ 规划协调 Agent 汇总、判断是否补查或结束
→ 生成并校验 PlanResult
```

FastAPI、后台任务、SSE 队列、结果表和正式结果保存不在本对话接线；四 Agent 图独立成功后，再回到后端集成对话完成。

### 11.2 Agent 职责

1. **天气查询 Agent**
   - 输入：目的地和日期范围。
   - 工具：初期使用 Fake 天气工具，后续才考虑获授权的真实来源。
   - 输出：覆盖旅行日期的结构化天气结果。
   - 完成条件：需要的日期均有可用结果，或明确失败。

2. **景点规划 Agent**
   - 输入：目的地、日期、用户偏好和约束。
   - 工具：初期使用 Fake 景点搜索工具。
   - 输出：结构化候选景点、推荐信息及规划所需数据。
   - 完成条件：产生足以支持协调 Agent 排程的结果，或明确失败。

3. **酒店规划 Agent**
   - 输入：目的地、日期、人数、预算和住宿偏好。
   - 工具：初期使用 FakeHotelProvider/Fake 酒店工具。
   - 输出：满足基本约束的结构化酒店推荐结果。
   - 完成条件：得到可用推荐，或明确失败。

4. **规划协调 Agent**
   - 输入：原始请求、已有专业 Agent 结果、错误和协调轮次。
   - 能力：判断下一步调用哪个专业 Agent、是否需要补查、何时生成最终结果、何时失败。
   - 输出：结构化路由决策；信息充分时生成最终规划。
   - 约束：必须有最大协调轮数，防止无限循环。

三个专业 Agent 完成后返回协调 Agent。第一版先串行协调，暂不并行；并行执行及 State reducer 在四 Agent 串行闭环稳定后再决定。

### 11.3 LangChain 与 LangGraph 分工

- LangChain：各 Agent 内部的模型接口、消息、领域工具、工具调用循环和结构化输出。
- LangGraph：共享 Graph State、Agent 节点或子图、条件路由、回到协调 Agent 的循环、最大轮数、成功和失败终止。
- 确定性 Python：标识和时间等执行元数据、费用加总、必要的业务校验及最终 Pydantic 校验。

### 11.4 分阶段开发顺序

每个阶段以约 2 小时的小单元推进，目标在约 2～4 轮对话内完成“讲解与任务 → 学习者实现 → 审阅修正 → 验证验收”；不为了凑轮次拆碎简单问题，也不因对话数目标跳过理解和验证。当前阶段未验收前不进入下一阶段。

1. **四 Agent 契约**
   - 明确每个 Agent 的输入、可用工具、结构化输出、完成条件和失败条件。
   - 避免专业 Agent 与协调 Agent 职责重叠。

2. **Graph State 与中间模型**
   - 初始输入：`request`。
   - 专业产物：天气、景点、酒店的结构化 Agent 结果。
   - 协调状态：下一 Agent/协调决策、协调轮次。
   - 错误状态：专业 Agent 或协调失败信息。
   - 最终结果：`result: PlanResult`。
   - 当前已有 `backend/graph_state.py` 只是第一次 `TypedDict` 练习，不是最终多 Agent State；在 Agent 输出契约明确后由学习者亲手扩展。

3. **三个 Fake 领域工具**
   - 分别实现并独立验证 Fake 天气、景点和酒店工具。
   - 工具只负责接收参数并返回结构化数据，不负责最终行程规划。

4. **三个专业 Agent**
   - 建议依次完成天气查询 Agent、景点规划 Agent、酒店规划 Agent。
   - 每个 Agent 独立完成模型/角色指令、工具绑定、工具调用、结构化输出、正常路径、工具失败路径和测试。
   - 初期使用 Fake/Stub 模型和 Fake 工具，不接入真实外部 API，不读取或回显凭据。

5. **规划协调 Agent**
   - 根据 State 选择 `weather`、`attraction`、`hotel`、`finalize` 或 `fail`。
   - 能发现缺失或不足的专业结果并请求补查。
   - 有最大协调轮数，并能解释失败原因。

6. **父 LangGraph**
   - 构建 `START → coordinator`。
   - 协调 Agent 条件路由到三个专业 Agent、最终校验或失败终点。
   - 三个专业 Agent 完成后返回协调 Agent。
   - 学习并验证 Agent 节点/子图、条件边、循环、`compile()` 和 `invoke()`。

7. **PlanResult 生成与校验**
   - 协调 Agent 使用 `PlanRequest` 和三个专业结果生成完整规划。
   - 最终输出必须是通过现有 `PlanResult` Pydantic 模型校验的对象。
   - 确定性字段和费用计算不交给模型自由猜测。

8. **独立多 Agent 测试与验收**
   - 验证四个 Agent 能独立运行。
   - 验证协调 Agent 能选择下一专业 Agent并接收返回结果。
   - 验证信息不足时补查、循环上限、专业 Agent 失败和总体失败路径。
   - 验证成功时产生 `PlanResult`，失败时不伪造结果。
   - 验证模块不依赖 FastAPI、SSE、任务表或结果表即可运行。

### 11.5 LangGraph 模块完成标准

- 四个 Agent 均有独立、明确且经过验证的契约。
- 三个专业 Agent 均具有模型—工具—结果闭环，而不是改名后的普通函数。
- 协调 Agent 能根据 State 自主选择专业 Agent、补查、完成或失败。
- LangGraph 显式表达共享状态、条件路由、循环和终止。
- 使用 Fake/fixture 时可以稳定复现成功和失败路径。
- 独立调用图能够返回经过 `PlanResult` 校验的最终结果。
- 不接入真实外部 API 也能完成模块验收；真实 Provider 接入另行推进。
- 未修改或重新设计已经验收的 FastAPI、SSE 和结果查询契约。
